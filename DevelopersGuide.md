# 🛠️ Pravah Developer Guide

This guide provides technical instructions for integrating **Pravah** into your ecosystem.

## 1. Getting Started (Deployment)
Pravah is containerized and ready for deployment using Docker Compose.

```bash
export SUBSCRIPTION_JWT_SECRET="$(openssl rand -hex 32)"
export ADMIN_API_KEY="$(openssl rand -hex 32)"
docker compose up -d --build pravah-go db
```
Ports are intentionally not published to the host. Access `pravah-go:3000` from
the Compose network, by container IP, or through a configured reverse proxy.

Connection and request limits are configurable:

| Environment variable | Default | Supported range |
| --- | ---: | ---: |
| `SSE_HEARTBEAT_INTERVAL_SECONDS` | 30 | 5-300 |
| `CLIENT_SIGNAL_BUFFER` | 64 | 1-10000 |
| `MAX_SUBSCRIPTION_STREAMS` | 32 | 1-128 |
| `MAX_REPLAY_EVENTS` | 1000 | 1-100000 |
| `MAX_REQUEST_BODY_BYTES` | 16384 | 1024-1048576 |
| `DATABASE_OPERATION_TIMEOUT_SECONDS` | 3 | 1-30 |
| `COOKIE_SECURE` | true | boolean; use false only for local HTTP |
| `COOKIE_SAMESITE` | lax | strict, lax, none |
| `COOKIE_DOMAIN` | empty | optional domain |
| `COOKIE_MAX_AGE_SECONDS` | 31536000 | 3600-315360000 |

For production, use HTTPS with `COOKIE_SECURE=true`. `COOKIE_SAMESITE=none`
requires secure cookies.

If a client buffer fills, Pravah closes that connection instead of silently
dropping signals. A reconnecting client can replay retained events by event ID.

## 2. Registering Your Application
Before publishing events, you must register your parent application to obtain an API Key.

1.  Access the internal registration utility: `http://<container-ip>:3000/register.html`
2.  Alternatively, use the private API:
    ```bash
    curl -X PUT "$PRAVAH_URL/api/v1/register" \
         -H "Content-Type: application/json" \
         -H "X-ADMIN-KEY: <admin-api-key>" \
         -d '{ "name": "MyProjectName" }'
    ```
3.  Store the returned `apiKey` securely.

## 3. Client-Side Integration (SDK)

### Including the SDK
Add the lightweight SDK to your frontend application:
```html
<script src="https://pravah-service.com/js/pravah-sdk.js"></script>
```

### Initializing the Connection
The SDK automatically handles the identity handshake and tab synchronization.
```javascript
const pravah = new Pravah({
    baseUrl: 'https://pravah-service.com',
    streams: ['project:123', 'user:456'],
    subscriptionToken: '<short-lived-subscription-token>'
});
```

Issue a short-lived subscription token from your application backend. Tokens
authorize both live subscriptions and replay:

```bash
curl -X POST "$PRAVAH_URL/api/v1/subscriptions/token" \
     -H "Content-Type: application/json" \
     -H "X-API-KEY: <api-key>" \
     -d '{
       "streams": ["project:123", "user:456"],
       "subject": "user-123",
       "expiresIn": 900
     }'
```

### Listening for Signals
Register listeners for any event signal generated by your parent application:
```javascript
pravah.on('bid-updated', (signal) => {
    console.log('Signal received for ID:', signal.id);
    // Use your existing REST API to fetch fresh data using signal.id
    fetchMyProjectData(signal.id);
});
```

## 4. Tenant Retention
Each registered application has an independent replay retention configuration.
The registration endpoint accepts an optional `retentionHours` value; otherwise
`EVENT_RETENTION_HOURS` is used, with a default of 24 hours.

Update an application's retention period through the authenticated configuration endpoint:

```bash
curl -X PUT "$PRAVAH_URL/api/v1/config" \
     -H "Content-Type: application/json" \
     -H "X-API-KEY: <api-key>" \
     -d '{ "retentionHours": 72 }'
```

## 5. Server-Side Publishing
Trigger real-time signals from your backend using the `POST /pravah/publish` endpoint.

**Endpoint:** `POST /pravah/publish`
**Headers:**
- `X-API-KEY`: Your registered application API Key.
- `Content-Type`: `application/json`

**Payload:**
```json
{
  "streamId": "project:123",
  "event": "user-login",
  "data": {
    "id": "user-456"
  }
}
```

Publishing accepts only the event name, stream ID, and resource ID. Additional
payload fields are rejected. Reconnecting clients automatically replay retained
events by sending the standard `Last-Event-ID` header.
The publish response includes `persisted` and `replayable`. If MongoDB is
temporarily unavailable, accepted signals are delivered live with both fields
set to `false`.

## 6. Monitoring
Monitor the service health and active connection metrics:
- **Endpoint:** `GET /pravah/health`
- **Metrics:** Active SSE connections, Database status, Uptime.

## 7. Security Policy
Pravah enforces a **Signal-Only** policy. Do NOT pass sensitive data in the `data` object. Only pass the identifier (`id`) of the resource that was updated. The frontend is responsible for fetching the actual data through secure channels.
